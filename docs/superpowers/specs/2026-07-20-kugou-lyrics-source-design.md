# 酷狗音乐歌词源支持设计

## 目标

让歌词组件把酷狗音乐作为网易云音乐、QQ 音乐之外的第三个可选歌词源，并让“智能匹配最佳歌词”能够在三个来源之间选择最佳结果。

本次只支持酷狗标准 LRC 行级歌词。酷狗 KRC 逐字歌词、KRC 内嵌翻译和罗马音不在本次范围内。

## 当前状态

- 后端 `KuGouMusicService` 已能通过酷狗歌曲搜索接口获取歌曲信息和封面，但不能获取歌词。
- 后端 `LyricService` 仅能指定网易云或 QQ 作为歌词源，智能匹配也只比较这两个来源。
- 前端歌词设置页只展示网易云和 QQ 两个选项。
- 前后端已有 `Lyric` 数据结构、REST/WebSocket 传输协议和 LRC 解析逻辑，无需扩展协议。

## 方案选择

采用在现有结构上扩展的方案：

1. 在后端扩展 `KuGouMusicService`，加入歌曲匹配、歌词候选匹配和标准 LRC 下载。
2. 在 `LyricService` 中加入酷狗指定源路由，并把智能匹配从固定双源比较扩展为三源比较。
3. 在前端歌词源选项中加入酷狗音乐，继续使用现有 `parseLrc` 渲染。

不在本次将所有歌词服务重构为统一 Provider 接口。该重构会扩大改动范围，而当前三个服务的既有调用方式足以实现目标。

## 后端组件

### 酷狗 HTTP 客户端

新增一个只负责 GET 请求的小型客户端。生产实现继续使用项目现有的 Jsoup 请求方式，并设置连接与读取超时。`KuGouMusicService` 通过构造器接收该客户端，使单元测试可以注入固定响应而不访问真实网络。

客户端不包含歌曲选择、歌词候选选择或 Base64 解码逻辑。

### 酷狗歌曲结果

酷狗歌词搜索要求歌曲的 `FileHash` 和时长。现有公开 `Track` 对象没有 `FileHash`，且不应为了内部接口参数改变公共 Track JSON 结构。

因此在酷狗服务包内增加内部歌曲结果类型，保存：

- 已构造的 `Track`
- 酷狗 `FileHash`

公开的 `search(String keyword)` 仍返回 `Track`，封面等既有调用方无需改动；歌词获取流程使用内部结果取得 `FileHash`。

### 酷狗歌词获取

`KuGouMusicService.getLyric(String keyword)` 执行以下流程：

1. 用现有窗口标题解析逻辑取得真实歌名和歌手。
2. 调用酷狗歌曲搜索，最多检查前五个结果，并用 `SongMatchingUtil` 选择匹配度最高的歌曲。
3. 若匹配度低于现有精确匹配阈值，则返回带真实歌名、歌手和 `source="kugou"` 的空歌词。
4. 使用歌曲 `FileHash`、时长和关键词调用酷狗歌词候选搜索接口。
5. 在候选中比较歌名、歌手和时长，优先选择歌曲相似度最高、时长差最小的候选。
6. 调用歌词下载接口，请求 `fmt=lrc`、`charset=utf8`。
7. Base64 解码响应内容，并验证歌词包含有效 LRC 时间标签。
8. 构造现有 `Lyric` 对象：设置来源、歌名、歌手、时长、`hasLyric` 和 `lrc`。

酷狗结果不设置 `hasKaraokeLyric`、`karaokeLyric`、`hasTranslatedLyric` 或 `translatedLyric`。

### 歌词源路由

当关闭智能匹配时，`LyricService` 按以下规则路由：

- `netease`：网易云音乐
- `qq`：QQ 音乐
- `kugou`：酷狗音乐
- 其他未知值：回退网易云音乐

保留现有周杰伦在网易云来源下回退 QQ 的行为；用户明确选择酷狗时不执行该特殊回退。

### 三源智能匹配

开启智能匹配时，网易云、QQ、酷狗三个请求并行执行。每个请求独立捕获异常，单个来源失败不会取消其他来源。

选择过程分两步：

1. 计算窗口标题与每个非空结果的歌名、歌手相似度，排除未返回结果的来源。
2. 在歌曲匹配度接近或时长接近的候选间比较歌词完整度。

歌词完整度沿用现有评分：

- 有普通歌词：1 分
- 有翻译歌词：1 分
- 有逐字歌词：1 分

先选择歌曲匹配度明显更高的结果。匹配度接近时选择完整度得分更高的结果；得分相同时优先用户配置的歌词源。若配置源不在并列候选中，则按稳定顺序 `netease`、`qq`、`kugou` 选择，避免结果随机变化。

三个来源都失败时，返回以用户配置源为 `source` 的空歌词。

## 前端组件

把歌词源键、显示名称和图标路径提取为纯配置，包含：

- `netease` / 网易云音乐 / `/assets/netease_icon.png`
- `qq` / QQ 音乐 / `/assets/qq_icon.png`
- `kugou` / 酷狗音乐 / `/assets/kugou_icon.png`

歌词设置页根据该配置渲染 Tabs。仓库已经包含酷狗图标，无需增加图片资源。

“智能匹配最佳歌词”的说明从“同时从两种歌词源获取歌词”改为“同时从多个歌词源获取歌词”。

播放器收到 `source="kugou"` 时不增加专用解析分支。因为酷狗只返回普通 LRC，现有 `hasKaraokeLyric=false` 分支会直接调用 `parseLrc`。

## 错误处理

- 酷狗歌曲搜索状态码异常、结果为空或结构缺失：记录错误并返回空歌词。
- 歌曲匹配度不足：返回空歌词，避免同名歌曲或错误版本串词。
- 歌词候选为空：返回空歌词。
- 下载状态码异常、内容为空、Base64 无法解码、UTF-8 内容无有效时间标签：返回空歌词。
- 网络超时或连接失败：指定酷狗源时返回空歌词；智能匹配时继续使用其他成功来源。
- 所有失败路径都保持 `source="kugou"` 或用户当前配置源，方便前端和日志识别实际请求来源。
- 失败不改变 REST 或 WebSocket 消息结构，也不阻断歌词更新事件。

## 兼容性

- 保持现有 `/api/lyric`、歌词设置 API 和 WebSocket 数据结构不变。
- 现有 `settings-lyric-common.json` 中的 `netease`、`qq` 值继续有效。
- 新值 `kugou` 通过现有字符串字段持久化，不需要配置迁移。
- 未知或损坏的歌词源配置回退网易云音乐。
- 不改变 `Track` 公共字段，避免影响歌曲信息 API 的消费者。

## 测试策略

### 后端单元测试

使用 JUnit 5 和 Mockito，所有酷狗 HTTP 响应使用固定夹具，不依赖网络。按 TDD 顺序覆盖：

1. 歌曲搜索选择歌名、歌手匹配度最高的结果，并保留对应 `FileHash`。
2. 歌手或特殊版本错误的歌曲不会被当作精确匹配。
3. 歌词候选按歌曲相似度和时长差选择。
4. 标准下载响应能够 Base64 解码为 UTF-8 LRC。
5. 空候选、错误状态、无效 Base64、空内容和无时间标签均生成空歌词。
6. `lyricSource="kugou"` 时路由到酷狗服务。
7. 智能匹配会请求三种来源。
8. 单个来源异常时仍选择其他成功来源。
9. 完整度同分时优先用户配置来源，并保持稳定的后备顺序。

若当前 Maven 默认 Surefire 版本不能运行 JUnit 5，则在 `pom.xml` 中明确配置兼容版本。

### 前端测试

歌词源配置保持为无 React 依赖的纯 TypeScript 数据。使用 Node 内置测试运行器验证：

- 恰好包含 `netease`、`qq`、`kugou` 三个键。
- 酷狗显示名称和图标路径正确。
- 默认歌词源仍为 `netease`。

不为一个静态选项引入 React Testing Library 或其他大型测试依赖。

### 完整验证

- 后端运行完整 Maven 测试和打包。
- 前端运行 Node 测试、TypeScript 检查和 Vite 生产构建。
- 使用真实酷狗接口进行一次只读冒烟测试，验证歌曲搜索、歌词候选搜索、LRC 下载和前端 `parseLrc` 解析链路。

## 完成标准

- 用户可在歌词设置页选择酷狗音乐并保存设置。
- 指定酷狗来源时，匹配歌曲能够显示酷狗标准 LRC。
- 智能匹配能够在网易云、QQ、酷狗之间稳定选择结果。
- 酷狗接口失败或返回错误歌曲时不会显示错误歌词，也不会破坏歌词组件更新。
- 前后端既有构建和新增测试全部通过。
